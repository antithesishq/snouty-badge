# Snouty Genesis multiplayer

Every badge runs the same Genesis console in deterministic lockstep and
only the pads cross the wire: one byte per player per Genesis frame.
This file is what the cart side has (peripherals, the per-frame pads, the
determinism guarantees, the input-source seam) and what it needs from the
transport (section 6). The N-player lockstep itself is
`lib/lockstep_n.zig` (docs/LOCKSTEP_N.md at the root, branch `party`);
the cable lockstep `lib/lockstep.zig` (2 players) is untouched.

Status 2026-10-05 (branch `genesis/mp4`): peripherals, determinism and the
local seam built and host-tested; no transport wired yet (section 5).

## 1. What is built

- **N pads per frame.** `Md.step_frame_pads(md, &pads, render)` takes
  `core.Pads` = 8 pad words (`core.Pad` bits; pad 1 first).
  `Md.step_frame(pad, render)` is pad 1 with the rest released, the old
  call, unchanged in behaviour.
- **Peripherals** (`core/ports.zig`), chosen per game at power-on
  (`Md.setup.cfg`, section 2) and kept by `Md.reset`:

  | `ports.Kind` | Port 1 | Port 2 | Cartridge | Pads |
  |---|---|---|---|---|
  | `pad1` (default) | pad 1 | empty | | 1 |
  | `pads2` | pad 1 | pad 2 | | 2 |
  | `tap1` | Team Player, pads 1-4 | pad 5 | | 5 |
  | `tap2` | pad 1 | Team Player, pads 2-5 | | 5 |
  | `taps` | Team Player, pads 1-4 | Team Player, pads 5-8 | | 8 |
  | `ea4way` | 4 Way Play, pads 1-4 (port 2 selects) | | | 4 |
  | `jcart` | pad 1 | pad 2 | J-Cart pads 3-4 at 38FFFE | 4 |

  `cfg.six` marks pads that are 6-button pads (bits 8-11 of the pad word:
  X Y Z Mode); only a Team Player reports them (ID 1, a third nibble).
  `cfg.absent` marks unplugged pads (Team Player ID F; a direct or 4 Way
  Play pad reads as an empty port). Direct ports, the 4 Way Play and the
  J-Cart carry 3-button pads only (the 6-button pad's TH counter is not
  emulated, SPEC.md section 5).
- **Protocols**, from public documentation only (no emulator code read):
  - Team Player: Plutiedev "Sega multitap" and Street Racer's pad driver
    as disassembled and commented by r57shell
    (gist.github.com/realmonster/ae8ef8ad3e89f9b3be72). TH high = idle, ID
    nibble 3; TH low starts a transfer (nibble F), each TR edge steps to the
    next nibble and TL follows TR (the acknowledge, immediate here): 0, 0,
    the four slot IDs, then per connected slot R L D U, St A C B (and Mode
    X Y Z for a 6-button pad), active low; F past the end.
  - 4 Way Play: Plutiedev "EA multitap". Port 2 all outputs, its bits 6-4
    pick the pad port 1 reads (0-3), 7 = the adapter, which reads 0 on the
    low data bits (detection: `$0C` then `$7C`, bits 1-0). TH from port 1.
  - J-Cart: as the emulation community describes it (no primary document
    found; unverified): word at 38FFFE = pad 4's lines in bits 13-8, pad
    3's in bits 5-0, each with TH in bit 6; bit 0 of a write to
    38FFFE/38FFFF sets TH for both. The register lives in the bus's SRAM
    window (`Md.sram` bytes 0-1, refreshed each frame and on a TH write),
    so the ROM read path gets no new check; a J-Cart game's header SRAM
    (none of the known ones) would be ignored.
- **Menu override**: the Reset row reads "Reset: Tap in 1" and so on;
  Left/Right pick what the reset plugs in, A resets with it (games look
  for their multitap at power on). It opens on what is plugged in now.
  Displaced: Left/Right on the Reset row used to scrub (XIP cart and
  simulator only; the RAM cart has no scrubber). `docs/mp_menu_reset.png`.
- **Lockstep mode** (`Md.setup.lockstep`) and the **poll hook**
  (`Md.setup.poll_hook`), section 3 and 6.
- **`Md.state_hash()`**: 32 bits over the whole console (`Md.Small` plus
  work RAM, VRAM, cartridge SRAM and Z80 RAM) minus what is not state
  (the 68000's fetch-window pointer, the VDP's sprite cache). About 154 KB
  of reads (an estimated 1-1.5 ms on the badge), so for a periodic desync
  check (`check_every` 32 ticks), not every frame.
- **The input-source seam** (`cart/src/frontend/players.zig`, section 5).

## 2. Peripheral table

`core/ports_table.zig`, generated by `tools/gen_ports_table.py` (the data
and its sources are in the script). Key: the header serial (0x180-0x18D),
plus the header checksum (0x18E) where the serial is a placeholder that
several games share. No match: a `4` in the header's device field
(0x190-0x19F, Sega's code for multitap support) gives `tap1`; otherwise
`pad1`. Sources: each game's ROM header dump on its Sega Retro "Technical
information" page; peripheral support from Sega Retro's "Team
Player-compatible games" and "4 Way Play-compatible games" categories;
the J-Cart titles from Sega Retro's and Wikipedia's J-Cart pages. Games in
both categories get the Team Player unless EA made them.

Verified with a real dump here: **Mega Bomberman** only (Adrian's,
`GM MK-1573-00`, checksum 29F3, CRC32 4BD6667D): Team Player detected, a
4-human battle reached, every pad moves its own bomber
(`tests/mp_bomberman.zig`). Every other row is unverified (identifiers
from the header dumps, no ROM here).

| Peripheral | Games (header serials in the generator) |
|---|---|
| Team Player (`tap1`) | Mega Bomberman (verified), Gauntlet IV, NBA Jam (US rev 0/1, JP), Columns III (US, JP), Dragon: The Bruce Lee Story (US, EU), Street Racer, Tiny Toon Adventures: ACME All-Stars, The Lost Vikings (US, EU), Party Quiz Mega Q, Puzzle & Action: Tant-R, Ichidant-R, Wimbledon Championship Tennis (US, EU), Hoops Shut Up and Jam!, Barkley Shut Up and Jam 2, World Championship Soccer II, Yuu Yuu Hakusho: Makyou Toitsusen, Pepenga Pengo, NBA Action '94, NBA Action '95, Prime Time NFL Football, College Football's National Championship |
| 4 Way Play (`ea4way`) | General Chaos (US, EU), FIFA International Soccer (two serials), FIFA Soccer 95 (rev 0/1), 96, FIFA 97 Gold Edition, FIFA Road to World Cup 98, NHL Hockey '94, NHL 95-98, Madden NFL '94 (two serials), '95, 96-98, NBA Live 95-98, NBA Showdown '94 (two serials), Bill Walsh College Football, '95, Rugby World Cup 1995, Mutant League Hockey |
| J-Cart (`jcart`) | Micro Machines 2: Turbo Tournament, Micro Machines Military, Pete Sampras Tennis '96, Super Skidmarks |

Left out, no header source found: NBA Jam Tournament Edition (Sega Retro's
dump has no header), Pete Sampras Tennis (J-Cart) and Micro Machines '96
(J-Cart). The menu override covers them.

**Six-button input.** The header's device field says `6` for: Dragon: The
Bruce Lee Story, Yuu Yuu Hakusho: Makyou Toitsusen, NBA Action '94 and
'95, Prime Time NFL Football, College Football's National Championship,
FIFA International Soccer (one release), FIFA Soccer 96, NBA Live 96 and
97, NBA Showdown '94. All of them also play on 3-button pads; Yuu Yuu
Hakusho (a fighting game) is the one that loses most without X Y Z. A
6-button player needs two bytes per frame (section 6); the badge has no
spare buttons for them anyway.

**What fits on a badge today.** The RAM cart (the show firmware's) plays
drive ROMs up to 768 KB (`romsrc.clusters`), and the 1,280 KB drive holds
about 730 KB beside the RAM cart's 548 KB UF2. Of the table only Columns
III (512 KB) fits; Mega Bomberman, Gauntlet IV, General Chaos, Street
Racer, the Micro Machines are 1 MB, most EA titles 2 MB. Running them on
badges needs more drive room (the unused 2 MB external flash, memory note
"SYCL external 2 MB flash") and a larger cluster table (or a no-table
path for contiguous files).

## 3. Determinism

Guarantee: with `Md.setup.lockstep` set, the console state after
`step_frame_pads` is a function of the state before and of the pads only.
Two badges with the same build and ROM stepped with the same pads have
equal `state_hash()` after every frame. Nothing in `core/` reads a clock,
`cart.rand`, the frontend or the drive layout.

Checked by `tests/mp_determinism.zig`: two consoles that differ in
everything a badge may do differently (memory filled with different
garbage before `init_in_place`; the ROM contiguous vs scattered over
512-byte drive clusters; rendering every second frame in squeeze/sharp vs
every frame in crop/Smooth H40; a poll hook on one) with the same 8-pad
script have equal hashes after every frame: test ROM 600 frames,
Miniplanets 900, Sonic 1 2400, Mega Bomberman 2400 (with its Team
Player). It runs on the full core (Z80 on) and on the RAM cart's (Z80
stub).

Audit (what could leak, and what was done):

| Candidate | Finding |
|---|---|
| Rendering (which frames, crop/squeeze, Smooth H40) | The renderer sets the sticky sprite overflow and collision bits, and only on the lines it renders, so they depended on the render pattern and options (Smooth H40 detects collision at all 320 columns). Lockstep mode drops what the renderer set (they read 0 there). Sonic 1 never showed a difference without it (it does not read them); a synthetic test does. |
| Reset of padded structs | `Ym2612.reset` (field by field) left its 3 bytes of tail padding as they were, so the hash and the undo records' byte compare saw old memory. `Md.reset` zeroes the small structs' bytes first. Found by the garbage-memory test. |
| Fragmented drive ROM | Same bytes through `rom.run_at` windows and DMA spans (already tested by `frag_mini.zig`); fetch-window pointers differ, so the hash skips them. |
| Background CRC32, the drive scan | Frontend only, read the ROM, never the console. |
| Sound (synthesis on/off, fast forward silence) | Reads the chips (`*const Md`); never writes the console. |
| `not_wait_loop` hint, the sprite cache | Not state: the skip is exact either way, the cache is rebuilt from VRAM. Excluded from the hash. |
| Wall clock, `cart.rand`, fast forward budget | Frontend only. Fast forward changes how many frames an update steps, never what a frame does; it must be off in a session anyway (section 6). |
| Build variant | The RAM cart (Z80 stub) and the XIP cart / simulator (Z80) are different machines: every badge of a session must run the same variant (section 6). |

## 4. Tests

- `tests/ports_unit.zig` (15): each peripheral through the 68000's I/O
  addresses as a driver does it: the Team Player handshake with the TL
  acknowledge, IDs and nibbles for 3-button, 6-button and empty slots on
  port 1, port 2 and both (8 pads), transfers starting over, a keyframe

  one-byte change in each region and ignoring the non-state fields.

## 5. The input-source seam

`cart/src/frontend/players.zig`:

- `next_frame(local_pad, &pads) bool`: the pads for the next Genesis frame.
  Today's only source, `local`, puts the badge's mapped pad on
  `local_player` (player 1) and releases the rest; it is always ready.
  app.zig's `run_update` steps every frame of the update with these pads.
- `pads_from_slots(in: *const [16]u8, present: u16, &pads)`: slot s's byte
  is pad s; a slot not present is a released pad (not an unplugged one).
  This is the body of a LockstepN `G.simulate(w, in, present)`.
- `wire_byte(pad) u8`: the byte a badge sends: the Genesis 3-button pad
  after this badge's own button layout (`U D L R A B C Start` = `core.Pad`
  bits 0-7), so a receiver needs nobody's settings.
- `networked` (comptime false today): fast forward and the chorded rewind
  are already gated on it in app.zig; the menu's Reset, Pick ROM and
  scrubbing must be too when a network source lands.
- `poll()`: the receive-ring drain, called at the top of every update;
  `Md.setup.poll_hook` calls into the transport five times inside every
  frame (lines 0, 64, 128, 192, 256: about every 3.5 ms of a 20-29 ms
  update). Both are no-ops until a network source exists, and the hook is
  a null test per 64 lines when not installed.

A LockstepN adapter (left for when `lib/lockstep_n.zig` is on main):
`G.World` = the console plus "render this tick" (the last frame of an
update renders), `simulate` = `pads_from_slots` + `step_frame_pads`,
`hash` = `state_hash`, `hand_over` = nothing (an absent slot already reads
released), `rules_len` = 5 (ROM CRC32, 4 bytes, plus the `ports.Kind`),
`stall_drop_ms` = 3000 (silence counts from a slot's last frame, so a 29
ms tick never trips it), `input_delay` runtime (GO carries it, 1-30).

## 6. Transport requirements (for the USB / party session)

- **Bytes per player per frame**: 1 (`wire_byte`, all 8 bits used, no
  reserved values). One tick = one Genesis frame (60 Hz of game time).
  A 6-button player would need 2 (bits 8-11); not planned (the badge has
  no buttons for them). A 4-player game is 4 bytes of input per tick;
  LockstepN's INPUT frame is 6 bytes on the wire per tick per badge.
- **Frame pacing**: the badge steps two Genesis frames per 30 Hz update
  (20-29 ms of work, SPEC.md section 8), so ticks arrive and are consumed
  in pairs, about 33 ms apart; a slow update stretches that. The game runs
  at the pace of the slowest badge. LockstepN's `send_every = 2` (one
  INPUT frame per update) would halve the relay's frame rate at no extra
  delay for us.
- **Draining**: the relay removes a player whose cart stops reading. The
  cart drains at the top of every update and five times inside every
  Genesis frame (`Md.setup.poll_hook`), so the longest gap is about 4 ms
  of emulation. A receive ring of 2 KiB (about 13 frames of small traffic)
  or LockstepN's default 4 KiB is plenty at that rate. Keep the
  `CartSerialRings` struct and both rings static (never on the stack: the
  OS may finish a pass after the cart stores 0).
- **Input delay**: a runtime lobby value (GO carries it), never comptime
  here. How it should feel in Mega Bomberman (estimates from the game's
  grid movement, not measured on a badge): each tick of delay is 16.7 ms on
  top of the 30 Hz present (one to two frames already). 1-3 ticks: not
  noticeable; 4-6: a slightly heavy pad, fine for a bomb game; 7-10
  (115-170 ms): turns at corners and bomb drops feel late, still playable
  for casual matches; 12+: sluggish, players overshoot corridors; 20+: not
  fun. One laptop needs 3 (docs/LOCKSTEP_N.md section 6); a network lobby
  should start from `suggested_delay()`.
- **ROM identity in the join**: every badge must run the same ROM bytes,
  the same build variant and the same peripheral. Carry in the host's
  rules: the ROM CRC32 (the cart computes it in the background, 8 KB per
  update: `romsrc.crc_tick`, 2 s for 512 KB, 4 s for 1 MB; a join must
  wait for it), the
  `ports.Kind` (one byte; plus `six`/`absent` masks if ever used), and
  the variant (RAM cart without Z80 vs XIP/simulator with: put it in the
  game id or `G.version`). A guest whose CRC differs must not ready.
- **Start**: all badges reset the console with the agreed `setup.cfg` and
  `setup.lockstep = true` at tick 0 (cartridge SRAM is in RAM and starts
  zeroed, so nothing badge-local survives).
- **A dropped player**: their pad goes idle (released) from the hand-over
  tick on every badge (`present` bit clear): the game keeps their
  character standing still; it does not see a pad unplugged (that would
  confuse games that only detect pads at boot). A rejoin (LEAVE plus a new
  HELLO) is a new player in the lobby, never mid-game.
- **Disabled while networked**: fast forward, the scrubber and the
  chorded rewind (they would step or rewind one badge alone), the menu's
  Reset and Pick ROM, and pausing the console from the menu (the menu
  must not stop the badge from consuming ticks; a pause has to be the
  session's pause bit). Sound may run (it never writes the console).
- **Desync check**: `state_hash()` reads about 154 KB (estimate: 1-1.5 ms
  on the badge, not benched); every 32 ticks is fine, every tick is not.
